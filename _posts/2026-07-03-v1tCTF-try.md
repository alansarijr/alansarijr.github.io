**v1t CTF - try Writeup**

**Category:** Reverse Engineering

**Difficulty:** Medium

**Objective:** Find the exact 22-character input that makes the binary print `[+] accepted`, by defeating anti-debug traps, decrypting a custom bytecode program, and inverting the validation math.

In this CTF competition, I tackled a Reverse Engineering challenge called **"try"**. On the surface it looked like a simple password checker. Underneath it had three layers: anti-debugging traps, an encrypted mini-program running inside a custom virtual machine, and a chain of reversible math that I needed to run backwards to get the flag. Here is how I broke it down.

---

# 1. First Look

The challenge gave me a single file: `chall.exe`. Before opening any disassembler, I ran basic recon commands to get a feel for the binary.

```bash
$ file chall.exe
chall.exe: PE32+ executable (console) x86-64, for MS Windows
```

So it is a 64-bit Windows executable. Then I pulled out readable strings:

```bash
$ strings chall.exe
...
WhatSoundDoesACowMake
Enigma protector v
CheckRemoteDebuggerPresent
IsDebuggerPresent
sealed input verifier
[+] accepted
[-] rejected
Ro.InK1+y+
```

Three things immediately stood out:

- **"Enigma protector"** — the binary is packed. Packers wrap a program in an extra shell that makes it harder to analyze, like putting a locked box inside another locked box.
- **Anti-debug imports** — `IsDebuggerPresent` and `CheckRemoteDebuggerPresent` tell me the binary will actively try to detect if I am using a debugger.
- **Encrypted blobs** like `Ro.InK1+y+` in the data section — these look like they are hiding something.

When I ran the binary it printed:

```
+----------------------------------------+
|       sealed input verifier            |
+----------------------------------------+
input > _
```

My goal was simple: find the exact string that makes it print `[+] accepted`.

---

# 2. Static Analysis

Since the binary detects debuggers, I did **static analysis** — reading the disassembly without ever running the binary. I used radare2:

```bash
$ r2 -A chall.exe
```

The main function (`fcn.00402962`) does five things in order:

1. Print the banner
2. Read the user's input via `fgets`
3. Strip the newline off the input
4. Run an anti-debug check and get back a key byte
5. Pass that key byte and the input to the validator

Everything interesting happens inside the validator. But before I could understand the validator, I needed to understand what the anti-debug check was doing.

---

# 3. The Anti-Debug Check

The anti-debug function (`fcn.004024d9`) runs three separate checks to see if someone is trying to analyze the binary.

**Check 1 — IsDebuggerPresent.** It calls a Windows API that asks the OS: "is a debugger attached right now?" If the answer is yes, the function returns the byte `0x13` and exits early.

**Check 2 — Thread context check.** The binary pauses its own thread and reads its register state. Under a debugger, certain register flags look different. If this check catches something, it returns `0x29`.

**Check 3 — Timing check.** It calls `QueryPerformanceCounter` twice with a 12ms sleep in between. If the elapsed time is larger than expected (because a debugger slows execution down while you are stepping through instructions), it returns `0x4e`.

If all three checks pass cleanly, the function returns **`0xa7`**.

This return value is not just a status code — it is used as an **encryption key** for everything that follows. The entire bytecode program is encrypted with `0xa7`. If you run the binary inside a debugger, you get a wrong key, the bytecode decrypts to garbage, and validation breaks no matter what you type.

Since I was doing static analysis, I just noted: under normal execution, `key = 0xa7`. I hardcoded this in my solver.

---

# 4. The Validator

The validator (`fcn.00402618`) takes the input string and the key byte `0xa7` and runs three checks:

1. The input must be exactly 22 characters long.
2. The input must pass a bytecode VM check.
3. A hash of the input must match a stored expected hash.

All three must pass. The flag constraints live inside check 2, the bytecode VM.

---

# 5. The Bytecode VM

Instead of writing a simple comparison, the author built a tiny **virtual machine** — a custom interpreter that runs its own secret instruction set. The program it runs (the "bytecode") is stored encrypted in the binary.

A virtual machine in this context is just a loop:

```
while there are instructions left:
    read the next opcode byte
    figure out which operation it means
    execute that operation
```

The trick is that "which operation it means" is defined by the author, not by x86. So I had to reverse-engineer both the interpreter and the program it runs.

## Spotting the VM

When I opened `fcn.00401fb8` in radare2, the first thing I noticed was that it did not look like a normal validation function. A normal check would load a few values, compare them, and return. This function was almost 1300 bytes long and had a loop at its core that kept jumping back to the same starting point.

The loop structure looked like this in the disassembly:

```asm
0x401ff9:  call fcn.00401a3f   ; read next byte into var_11h
           cmp  eax, 0         ; did we run out of bytecode?
           je   0x4024d7       ; if yes, exit
           jmp  0x402470       ; otherwise, dispatch

0x402470:  cmp  var_11h, 0x71  ; is the opcode 0x71?
           jge  0x4024ac       ; ...
           cmp  var_11h, 0x18  ; is it 0x18?
           je   0x4021d5       ; jump to that handler
           cmp  var_11h, 0x32  ; is it 0x32?
           je   0x40213b       ; ...
           ...

0x4024d2:  jmp  0x401ff9       ; loop back
```

Three things immediately identified this as a VM:

**A program counter.** The variable `var_8h` was a `qword` initialized to zero, incremented every time `fcn.00401a3f` was called, and checked against a maximum (`0x16d`). This is exactly what a program counter does — it tracks which instruction to execute next.

**A dispatch loop.** The pattern of "read one byte, compare it against a list of known values, jump to the matching handler, loop back" is the textbook structure of a bytecode interpreter. In compiled code you rarely see a loop that reads one byte at a time and then chains through a series of `cmp/je` pairs like this.

**Handler functions with shared state.** Each handler read additional bytes (the operands) from the same stream using the same `fcn.00401a3f` call, and they all modified the same small set of variables (`var_9h`, `var_ah`, `var_bh`). These are the VM's registers.

Once I recognized the pattern, the approach became clear: figure out what each opcode byte means, then read the program the VM is running.

## Finding and Decrypting the Bytecode

The encrypted bytecode sits at file offset `0x2fa8`. Here is what the raw bytes look like:

```
a6 81 83 b7 74 ef de a7 ab bb b7 4f dc b3 03 32 ...
```

These bytes are meaningless until decrypted. To understand how, I traced the function responsible for reading them.

**Finding the reader function.**

Every time the VM needed the next bytecode byte, it called `fcn.00401a3f`. That function was called over and over in every handler, always with the same three arguments: a pointer to the program counter (`var_8h`), the key byte (`arg2 = 0xa7`), and a pointer to an output variable where the decoded byte should be stored.

I opened `fcn.00401a3f` in radare2 and read through it:

```asm
; fcn.00401a3f (rcx = &pc, rdx = key, r8 = &output)

mov  rax, [rcx]          ; rax = current pc value
cmp  rax, 0x16d          ; is pc >= 365? (bytecode length)
jb   continue
mov  eax, 0              ; if yes, return 0 (end of bytecode)
ret

continue:
mov  eax, [rcx]          ; eax = pc
add  qword [rcx], 1      ; pc++
lea  rax, [0x4043a8]     ; base address of bytecode in memory
add  rax, rdx            ; rax = bytecode[pc]
movzx ecx, byte [rax]    ; ecx = raw encrypted byte

; --- compute hash_byte(pc, key) ---
call fcn.0040199f        ; result in al

; --- xor then rotate ---
xor  ecx, eax            ; decoded = raw ^ hash
and  ecx, 0xff
xor  eax, edx            ; rotation = (pc ^ key) & 7
and  eax, 7
call fcn.004018ed         ; rotate_right_8(decoded, rotation)

mov  [r8], al            ; store result in *output
mov  eax, 1              ; return 1 (success)
ret
```

So every bytecode byte goes through two steps before it is used: XOR with a hash value, then a bit rotation. Both depend on the byte's position and the key `0xa7`.

**Understanding the hash function (`fcn.0040199f`).**

I then opened `fcn.0040199f` to understand what the "hash value" actually was. Here is what the disassembly showed, translated into Python:

```python
def hash_byte(position, key):
    # Step 1: process the key
    a = (key * 0x45d9f3b) & 0xffffffff
    a ^= 0x6d2b79f5

    # Step 2: process the position using the golden-ratio constant
    b = (position * 0x9e3779b9) & 0xffffffff

    # Step 3: combine them
    v = (a ^ b) & 0xffffffff

    # Step 4: avalanche mixing (standard bit scrambling pattern)
    v ^= (v >> 16)
    v  = (v * 0x7feb352d) & 0xffffffff
    v ^= (v >> 15)
    v  = (v * 0x846ca68b) & 0xffffffff
    v ^= (v >> 16)

    # Step 5: fold the 32-bit result into one byte
    return (v ^ (v>>8) ^ (v>>16) ^ (v>>24)) & 0xff
```

The constant `0x9e3779b9` is the 32-bit approximation of `2^32 / golden ratio`. It appears in hash functions like Fibonacci hashing because it distributes values evenly across the integer space. Its presence here told me this was not a quick-and-dirty XOR cipher — the author put effort into making each position's key byte unpredictable.

**Understanding the rotation (`fcn.004018ed`).**

After the XOR step, the decoded byte is further scrambled by rotating its bits. The rotation amount is `(position XOR key) & 7`, which gives a value from 0 to 7 — a different rotation for every position. This function was a simple 8-bit right rotation:

```python
def rotate_right_8(value, n):
    n = n & 7
    if n == 0:
        return value & 0xff
    return ((value >> n) | (value << (8 - n))) & 0xff
```

**Putting it together.**

With both sub-functions understood, the full decryption of one bytecode byte is:

```python
def decrypt_byte(raw_byte, position, key=0xa7):
    h   = hash_byte(position, key)          # unique value for this position
    dec = (raw_byte ^ h) & 0xff             # undo the XOR encryption
    rot = (position ^ key) & 7              # compute rotation amount
    return rotate_right_8(dec, rot)         # undo the bit rotation
```

I applied this to all 365 bytes at offset `0x2fa8` and the result was readable bytecode.

## Reading the Instruction Set

After decrypting all 365 bytes I could read the VM's dispatcher. It is a big switch statement that maps opcode bytes to operations. I traced each case:

| Opcode | What it does |
|--------|-------------|
| `0x4b` | Load one character from the input into the accumulator |
| `0x71` | XOR the accumulator with the operand byte |
| `0x32` | Add the operand byte to the accumulator (mod 256) |
| `0x18` | Rotate the accumulator left by the operand amount |
| `0xd4` | Check: accumulator must equal the operand. Fail if not. |
| `0xa9` | Cross-check: verify a relationship between two input characters |
| `0x5d` | Update internal state (does not affect the flag check directly) |
| `0xee` | End: return pass or fail |

## Reading the Bytecode Program

With the instruction set mapped, the decrypted bytecode revealed a clear structure:

- **22 rounds** — each checks one character of the 22-character input
- **11 pair checks** — each checks a relationship between two characters
- **1 end instruction**

Each of the 22 rounds follows the exact same pattern, just with different values:

```
LOAD   input[idx]     — put one input character in the accumulator
XOR    xor1           — scramble it
ADD    add_v          — scramble it more
ROTATE rot            — rotate the bits
XOR    xor2           — scramble again
CHECK  expected       — the result must equal this byte
```

Here are the first three rounds as an example:

```
Round  0: LOAD input[18], XOR 0xdc, ADD 0x50, ROT 6,  XOR 0x93, CHECK 0x8e
Round  1: LOAD input[17], XOR 0xdf, ADD 0x68, ROT 4,  XOR 0xfb, CHECK 0x4e
Round  2: LOAD input[ 4], XOR 0xa7, ADD 0xd8, ROT 3,  XOR 0x38, CHECK 0x58
```

# 6. Recovering the Flag

Here is the key insight that made this solvable in one shot: **every operation the VM uses is reversible**.

- XOR is its own inverse: `A XOR K XOR K = A`
- Adding K can be undone by subtracting K (mod 256)
- Rotating left by N can be undone by rotating right by N

So instead of brute-forcing all possible 22-character inputs, I just ran each round's operations backwards to directly calculate what character was required.

For round 0, the VM computes:

```
result = input[18]
result = result XOR 0xdc
result = (result + 0x50) mod 256
result = rotate_left(result, 6)
result = result XOR 0x93
check:   result == 0x8e
```

Running it backwards:

```
v = 0x8e XOR 0x93              — undo the last XOR
v = rotate_right(v, 6)         — undo the rotation
v = (v - 0x50) mod 256         — undo the addition
v = v XOR 0xdc                 — undo the first XOR
→ input[18] must be this value
```

The solver does this for all 22 rounds at once:

```python
with open('chall.exe', 'rb') as f:
    filedata = f.read()

bytecode_raw = filedata[0x2fa8:]
decoded = [decrypt_byte(bytecode_raw[i], i) for i in range(0x16d)]

flag = [0] * 22

for rnd in range(22):
    ops      = decoded[rnd * 14 : (rnd + 1) * 14]
    idx      = ops[3] % 22    # which input character
    xor1     = ops[5]
    add_v    = ops[7]
    rot      = ops[9]
    xor2     = ops[11]
    expected = ops[13]

    v = expected ^ xor2             # undo XOR2
    v = rotate_right_8(v, rot)      # undo rotation
    v = (v - add_v) & 0xff          # undo ADD
    v = v ^ xor1                    # undo XOR1

    flag[idx] = v

print("Flag:", bytes(flag).decode())
```

No brute-force. No guessing. Each character drops out directly from the math.

I verified the result against the 11 pair-checks as well — all passed.

# 7. Final Flag

```
v1t{n0_dump_just_pain}
```

The message "no dump, just pain" is the author's own commentary on the challenge. The binary was built specifically to resist memory dumping and dynamic debugging. The intended path was patient static analysis: decrypt the bytecode by hand, read the VM, and invert the math.

---

# 8. Conclusion

This challenge was a great exercise in:

- **Anti-Debug Awareness:** The return value of the check was a key that encrypted the rest of the validation. Bypass it wrong and everything else breaks.
- **VM Reversing:** A VM is just a loop with a switch statement. Once you map the opcodes to operations, the "secret program" becomes readable like any other code.
- **Algebraic Inversion:** Recognizing that every operation was reversible meant skipping brute-force entirely and solving it algebraically.
